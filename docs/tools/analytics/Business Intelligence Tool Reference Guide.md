# Business Intelligence Tool Reference Guide

The `bi_*` tools answer questions about **metrics**: business measures (net sales, order count,
average order value) that an owner defines once in a YAML file, so every caller gets the same
answer and nobody writes SQL. The design (metric file format, compilation, governance) is in
[Business Intelligence](../../architecture/Business%20Intelligence.md); terms are in the
[Glossary](../../../GLOSSARY.md).

Every tool is read-only and closed-world, and no metric tool takes SQL: a caller names a metric, the
metric's declared dimensions and grains, filters as `{dimension, op, value}` (values bound as
parameters) and a period. Results depend on who calls (a metric's `roles`), so the tools are not
cached.

## Out of the box

Three sample metrics ship in `config/bi/metrics/` over the DuckDB sample data (`data/duckdb/orders.csv`,
the `orders` table of the `duckdb_*` tools), dated January 2023 to November 2024:

| Metric | Type | What |
|---|---|---|
| `net_sales` | sum | completed orders' quantity × unit price after the line discount |
| `order_count` | count | completed orders |
| `average_order_value` | ratio | `net_sales` / `order_count` |

All three have the dimensions `region`, `product_category`, `payment_method` and `sales_rep`.

## Calling the tools

A typical path: `bi_list_metrics`, then `bi_describe_metric` for a metric's dimensions and grains,
then a question.

| Question | Call |
|---|---|
| Net sales by region per quarter in 2024 | `bi_query_metric {"metric": "net_sales", "by": ["region"], "grain": "quarter", "period": "2024"}` |
| Orders this quarter against last quarter | `bi_compare {"metric": "order_count", "period": "QTD"}` |
| Q3 2024 against Q3 2023, by region | `bi_compare {"metric": "net_sales", "period": "2024-Q3", "against": "same_period_last_year", "by": ["region"]}` |
| Who makes 80 percent of sales | `bi_top_n {"metric": "net_sales", "dimension": "sales_rep", "period": "2024", "pareto": true}` |
| Sales by region and category, as a share of each row | `bi_crosstab {"metric": "net_sales", "rows": "region", "columns": "product_category", "period": "2024", "normalize": "row"}` |
| Why did average order value fall in Q3 2024 | `bi_explain_change {"metric": "average_order_value", "period": "2024-Q3", "against": "2024-Q2", "dimensions": ["region"]}` |

Relative periods (`YTD`, `QTD`, `MTD`, `last 12 months`) end today, so on the sample data they find
nothing; use the calendar forms there.

`bi_explain_change` reports, per dimension, each member's contribution to the change and the
fewest members that explain most of it. For a sum or count the members' changes add up to the
total change. For a ratio such as `average_order_value` each member's contribution is split into a
**rate effect** (its own ratio moved) and a **mix effect** (its share of the denominator moved);
both add up exactly to the change of the overall ratio. Distinct counts, averages, minima and
maxima do not add up over members, so their members are ranked by their own change only.

## Errors

| Message | Meaning |
|---|---|
| `unknown metric 'x'` | no such metric, or your roles may not query it (the two look the same) |
| `x has no dimension 'y'` | `by`, `filters`, `rows`, `columns` or `dimension` names a dimension the metric does not declare |
| `x may be asked by day, week, ...` | the grain is not one the metric allows |
| `column(s) ... are masked on connection c` | the metric uses a column its data connection masks; fix the metric |
| `table t is not available on connection c` | the connection does not allow (or denies) the metric's table |
| `cannot read the period` | the period is not one of the forms in the domain description |
