## Overview

The sanctions tools (prefix `sanctions_`, configs `config/tools/sanctions/`, implementation
`sajha/tools/impl/sanctions_tools.py` over the package `sajha/sanctions/`) screen names against
the official sanctions lists. The lists are downloaded into a **local index**, so a name being
screened never leaves the machine and no API key is needed. Every result says that it is a
**screening aid, not a determination** (GLOSSARY "Sanctions screening"): a candidate match is
for a person to review against the official entry.

The design, the terms of each source and the owner's decisions are in
[Open Data Tools](../../architecture/Open%20Data%20Tools.md). The live catalog (`tools/list`, or
the Tools page) is authoritative for the tools and their schemas.

## The lists

| List id | Source | File |
|---|---|---|
| `ofac_sdn` | US Treasury, OFAC: Specially Designated Nationals and Blocked Persons | `SDN.XML` from the OFAC sanctions list service |
| `ofac_consolidated` | US Treasury, OFAC: the consolidated non-SDN lists | `CONSOLIDATED.XML` from the same service |
| `eu` | European Commission: EU Financial Sanctions Files, consolidated list | XML v1.1, found through the EU RSS feed |
| `uk` | FCDO: UK Sanctions List | `UK-Sanctions-List.xml` |
| `un` | UN Security Council Consolidated List | **disabled**: off until legal approves its terms of use; every tool refuses `un` |

The URLs are in `sajha/sanctions/sources.py`. Each result carries the attribution line of every
list it used in `source` (the EU reuse notice, the UK Open Government Licence, OFAC).

Entry ids are the list's own: the OFAC `uid`, the EU `logicalId` (the EU reference number such
as `EU.27.28` is in `reference`), the UK `UniqueID` (such as `AFG0006`). Countries are ISO 3166
alpha-2 codes where the list's country name is recognised, otherwise the list's own text. Dates
of birth keep the precision the list gives (`YYYY-MM-DD`, `YYYY-MM` or `YYYY`).

## The local index and its refresh

The index is a folder of files under `sanctions.data_dir` (default `data/sanctions`, git-ignored),
not database tables:

| File | Holds |
|---|---|
| `<list>.json.gz` | the parsed entries of one list, with its publication date and refresh time |
| `status.json` | per list: publication date, last refresh, last attempt, last error, entry and name counts |
| `changes.jsonl` | one line per refresh that changed a list: the entries added, changed and removed |

**Refreshing.** `sajha/sanctions/refresh.py` downloads each list through the outbound fetch guard
and HTTP proxy (`sajha/core/outbound.py`), parses it, compares it with the stored version (by entry
id, and a hash of each entry for changes), writes the new index and appends the diff. The EU file is
downloaded only when the EU feed shows a new publication (`force` overrides). A list that fails to
download or parse keeps its previous index and records the error. One refresh runs at a time per
data folder (a lock file). Each worker reloads a list when its file changes.

Three ways to run it:

- the shipped workflow `sanctions_refresh` (`config/workflows/sanctions_refresh.yaml`, daily at
  06:30 UTC), installed at start-up when no workflow of that name exists, owned by the
  administrator `admin` (`sajha/workflows/shipped.py`). To stop it, disable it on the Workflows
  page; a deleted shipped workflow is installed again at the next start;
- the `sanctions_refresh` tool, which only administrators may run;
- the command line:

```
python -m sajha.sanctions refresh [--list ofac_sdn --list eu] [--force]
python -m sajha.sanctions status
```

Until the first refresh, `sanctions_screen` and `sanctions_entry` fail with a message saying how
to refresh, and `sanctions_lists_status` shows each list as not loaded. Results state how old the
index is (`lists_searched` and `index`: publication date, last refresh, `age_hours`).

## How names are matched

All in `sajha/sanctions/match.py`, standard library only:

1. **Normalise.** Transliterate (accents removed by Unicode decomposition, plus letters it misses
   such as `ø` and `ß`; Cyrillic and Greek mapped to Latin), lower-case, turn punctuation into
   spaces (apostrophes are dropped), and remove honorifics and titles (`Dr`, `Sheikh`, `Haji`,
   `Colonel`, ...). For organisations, vessels and aircraft, common legal forms (`Ltd`, `GmbH`,
   `PJSC`, ...) are removed too. Names in other scripts are not indexed; their Latin aliases are.
2. **Score.** The token-set ratio (word order and extra words cost little), with a fifth weight on
   the token-sort ratio so that the exact name ranks above a longer name that contains it.
   Spelling variants of a word of at least four letters (85% similar) count as the same word. A
   one-word name against a longer name is scored on the whole sorted name, so one common word
   does not match every name that contains it.
3. **Phonetic key.** Each word gets a key in the Soundex family with every letter coded (so
   `Qadhafi`, `Kaddafi` and `Gaddafi` agree). When the keys of the shorter name are all found in
   the other (words of three letters or more), the score is lifted half way to 100
   (`phonetic_match: true`).

A match is reported when its score reaches `threshold` (default 85), once per entry, with the
alias that scored best (`matched_alias`). `date_of_birth` drops entries whose listed dates of birth
all disagree at the precision both have (entries with no date are kept, `dob_match: null`);
`country` never drops an entry, it ranks entries that list the country first (`country_match`).
At most 50 matches are returned (`truncated` says when there were more).

## Not for models: the shipped policy

Screening results are not given to a model (owner decision, Open Data Tools section 6). The
shipped policy `config/policies/10-sanctions.yaml` denies every `sanctions_*` call whose source is
`ask` (Ask SAJHA, an LLM tool's planner loop and a workflow's `ask` step, whose tool calls a model
chooses) or `openai_api`. People use the tools directly: MCP, the REST API, the console and
workflow tool steps are not affected. The rule language is in
[Policy and Audit](../../architecture/Policy%20and%20Audit.md).

## Calling the tools

```json
{"name": "sanctions_screen", "arguments": {"name": "Banco Nacional de Cuba", "lists": ["ofac_sdn"]}}
{"name": "sanctions_screen", "arguments": {"name": "Muammar Gaddafi", "type": "individual", "date_of_birth": "1942"}}
{"name": "sanctions_entry", "arguments": {"list": "ofac_sdn", "entry_id": "306"}}
{"name": "sanctions_changes", "arguments": {"since": "2026-10-01", "list": "eu"}}
{"name": "sanctions_lists_status", "arguments": {}}
```

## Limitations

- A screening aid, not a determination: fuzzy matching finds candidates and misses some
  spellings; review every candidate against the official entry and its identifiers.
- Changes are those between refreshes SAJHA ran; a list's first download is recorded as
  `initial` with no entries listed. OFAC's published delta file is not used: the whole list is
  downloaded and compared.
- Names written only in scripts other than Latin, Cyrillic and Greek are not screened.
- An LLM tool in `narrate` mode runs its fixed source as a model call (source `ask`), so the shipped
  policy also refuses a `sanctions_*` tool configured as a narrate source.
